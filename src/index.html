Which Work IQ tool when?

            
Want an answer? Use ask. Want the data? Use fetch for stored items, call_function for data Microsoft Graph computes, such as calendarView or delta(). Don't know where the data is? Use search_paths, then get_schema.

            

            
What a call costs

            
Documented in the Copilot Credits Guide (September 2026): Work IQ API usage is billed in Copilot Credits on two meters. Work IQ Tools API: static, "0.1 Copilot Credit per API call for actions and tools". Work IQ Chat or Context API: variable, for "grounding, retrieval, and reasoning", driven by models, runtime, context and tools; the guide's Light, Medium and Heavy examples give no credit figures. Pay-as-you-go list price: $0.01 per credit (USD, subject to change); pre-purchase plans list 5% to 20% discounts. Work IQ APIs are not included in Microsoft Copilot licenses; Work IQ inside Microsoft Copilot's own experiences has no incremental charge.

            
Background reasoning, per Microsoft's tool descriptions: only ask invokes Microsoft 365 Copilot, which reasons in the background and returns a written answer. The other tools read data, look up paths and schemas, or perform actions. In this harness, your model reasons over their results, billed as Azure OpenAI tokens.

            
This app's reading, because Microsoft publishes no per-tool meter table: ask counts as Chat; the nine other tools in Microsoft's ten-tool list count as Tools API, 0.1 per tools/call however many paths or items it covers; Microsoft does not document how a fetch with several paths is counted. ask counts as variable only: Microsoft does not document whether 0.1 also applies. fetch_blob and the CLI-only tools are not classified. Confirm this reading with your Microsoft account team before you budget.

            
Measured and estimated: the app records each answer's Work IQ requests and shows your model's tokens as the model reports them. The Copilot Credits line under an answer counts only the calls this app classifies as Tools API or Chat; other requests stay visible in Flow as not documented as billable. It multiplies the Tools API calls by 0.1, does not calculate the variable part, and is not a bill. Failed calls are counted; Microsoft does not document whether they are billed.

            
Where to check actual usage: the Microsoft 365 admin center (Copilot › Cost management) shows aggregate usage in credits by user, group, agent and service; it can include non-billable usage and is not a per-call bill. Recommendation: to size the variable part, run a pilot and compare its aggregate usage there. Billed amounts are in Azure Cost Management, under the Microsoft Copilot Studio service; they update daily, and usage can take up to 24 hours to appear.

            
Answers from Copilot

            

              
askGiven to the modelApp reading: Chat, variable credits

              
Microsoft 365 Copilot, or a chosen agent, finds the relevant mail, chats, meetings and files, reasons over them and answers in prose with links. Best for open questions. Slower, and you see only the sources it cites. "What did Sarah say about the launch date?"

              
list_agentsGiven to the modelApp reading: Tools API, 0.1 credit per call

              
Lists the agents available to the user; pass an agent's ID to ask. Send an HR question to a published HR agent.

            

            
Exact data

            

              
fetchGiven to the modelApp reading: Tools API, 0.1 credit per call

              
Reads stored items by path: messages, events, files, people. Several paths per call, one result each. Best when your model or code needs complete, precise data, or the details of an item that ask pointed to. For remote MCP, Microsoft documents 25 items by default, 100 at most, 10 chat messages per request, and $skip and $skiptoken blocked. /me/messages?$filter=isRead eq false&$select=subject,from

              
call_functionGiven to the modelApp reading: Tools API, 0.1 credit per call

              
Reads data that Microsoft Graph computes when you ask, one path per call: calendarView (meetings in a time range, recurring ones expanded), delta() (what changed in mail, events, contacts or chat messages), /me/chats/getAllMessages(), /me/onlineMeetings/getAllTranscripts(…), /sites/getAllSites(). In search_paths, most show as paths ending in (), but calendarView doesn't; which exist depends on tenant policy. Today's meetings: /me/calendarView?startDateTime=…&endDateTime=…

              
fetch_blobNot given to the modelMeter not documented

              
Downloads a file's bytes (PDF, Office file, photo), optionally converted to PDF, so your own code can process the document. The server's description says "Up to 4 MB for the raw file". Withheld here because Base64 content would flood the model's context.

            

            
fetch or call_function? Both only read. In a test on 23 September 2026, each tool also accepted the other's paths, and both rejected paging with $skiptoken. So follow Microsoft's intent above rather than a hard rule; results can differ by tenant policy. Paths that search_paths marks as actions, such as getSchedule, findMeetingTimes and /search/query, need do_action. reminderView, named in the tool's own description, returned "Access denied" in that test.

            
Finding paths and fields

            

              
search_pathsGiven to the modelApp reading: Tools API, 0.1 credit per call

              
Lists the available paths and their supported operations. The model's first step when it doesn't know where data lives. Filter: calendar

              
get_schemaGiven to the modelApp reading: Tools API, 0.1 credit per call

              
Returns the fields and parameters of a path and operation: which fields to $select, or what a create or update requires.

            

            
Changes (blocked by default by tenant policy, per Microsoft)

            

              
create_entityWithheldApp reading: Tools API, 0.1 credit per call

              
Creates an item. A meeting in /me/events, a draft in /me/messages.

              
update_entityWithheldApp reading: Tools API, 0.1 credit per call

              
Changes an item. Move a meeting to 4 pm, mark mail as read.

              
delete_entityWithheldApp reading: Tools API, 0.1 credit per call

              
Deletes an item. Delete a draft.

              
do_actionWithheldApp reading: Tools API, 0.1 credit per call

              
Runs an action with side effects. Send mail, accept a meeting, forward, move to a folder.

            

            
Microsoft documents mutation operations as blocked by default by tenant policy; tenant administrators can enable supported mutation scenarios through that policy. The current setting can differ by tenant: see . A harness should ask the user before each change. Use get_schema first to learn the required fields.

            
Local CLI only (version-specific)

            

              
retrieveWithheldMeter not documented

              
Raw search hits across Microsoft 365 and connected sources, with per-source metadata and citations. Useful for showing sources, but absent from the public tool reference: treat it as preview.

              
get_debug_link, accept_eulaWithheldMeter not documented

              
Create a shareable debug link for a conversation, and accept the CLI license. Both need a person's explicit confirmation.

    Why not call Microsoft Graph directly?
    
    
    Say a user asks your agent something nobody built a tool for: “Which Planner tasks are due this week?”
    
    
    
    
      
    
        
    With Microsoft Graph directly
    
        
    Before the agent can answer, a developer has to:
    
        
      
          
    1. Find GET /me/planner/tasks among Graph's 17,870 operations.
      2. 
          
    2. Write, test and ship a wrapper tool for it, like the one below.
      3. 
          
    3. Add the Tasks.Read permission to the app and get admin consent.
      4. 
          
    4. Repeat all three for every new kind of question.
      5. 
        
    
        
    // Illustrative, not part of this app: one wrapper per Graph endpoint.
// A real one also handles paging and throttling.
const listPlannerTasks = tool(async () => {
  const response = await fetch('https://graph.microsoft.com/v1.0/me/planner/tasks', {
    headers: { Authorization: `Bearer ${await graphToken(['Tasks.Read'])}` },
  });
  if (!response.ok) throw new Error(`Graph returned ${response.status}`);
  const { value } = await response.json();
  return JSON.stringify(value.map(({ title, dueDateTime }) => ({ title, dueDateTime })));
}, { name: 'list_planner_tasks', description: 'Planner tasks assigned to the user.', schema: z.object({}) });

    When Graph directly is the better fit
    
    
      
      
    • Your own code, not a model, knows the exact endpoint, for example a calendar-to-CRM sync.
      • 
      
    • Bulk or sync jobs: Graph supports paging, $batch, delta tokens and change notifications. For Work IQ's fetch, Microsoft documents at most 100 items and 10 chat messages per request, with $skip and $skiptoken blocked.
      • 
      
    • No signed-in user: Graph supports app-only permissions; Work IQ is delegated only.

    Authentication: what each route needs
    
    
    Who signs in where, and what an admin sets up once. Every route is delegated: Work IQ acts as the signed-in user, with that user's Microsoft 365 permissions. Application-only access isn't supported.
    
    
    Admin, once per tenant, for every route
    
    
      
      
    • Enable Work IQ. A Global Administrator creates the Work IQ service principal, for example az ad sp create --id fdcc1f02-fc51-4226-8753-f668596af7f7. Microsoft's MCP overview notes it's created automatically on first use, apart from corner cases.
      • 
      
    • Billing. A usage-based billing plan in Copilot Studio with an Azure subscription and resource group, and each user assigned to it. Until then, calls return 403; after assigning, allow 15 to 30 minutes.
      • 
      
    • Consent. WorkIQAgent.Ask is marked admin consent required, so each app that requests it needs admin consent. Without it, the first sign-in asks for admin approval.
      • 
    
    
    
    
      
    MCP, local
    
      
    1. This appStarts the bundled Work IQ CLI (workiq mcp) and speaks MCP over stdin and stdout. It never holds a Work IQ token.
    2. Work IQ CLISigns the user in with Microsoft's own app registration and keeps its own token cache. First run: workiq accept-eula.
    3. Microsoft Entra IDIssues the CLI a delegated token for Work IQ.
    4. Work IQ serviceThe CLI calls it with that token; Microsoft 365 data is read with the user's permissions.
    
      
    Admin, once: admin consent for the Work IQ application, as the CLI prerequisites require.
    
    
    
    
    
      
    MCP, remote
    
      
    1. This appBrowser sign-in (MSAL) with Microsoft's published Work IQ MCP client, callback port 12798, or with your own client ID.
    2. Microsoft Entra IDIssues a token for WorkIQAgent.Ask, the one scope the MCP endpoint's OAuth metadata advertises.
    3. Work IQ MCP endpointhttps://workiq.svc.cloud.microsoft/mcp; the token goes with every request.
    4. Microsoft 365Read with the user's permissions; changes only if the tenant's Work IQ MCP policy allows them.
    
      
    Admin, once: admin consent for WorkIQAgent.Ask for your own client ID, and a look at the Work IQ MCP policy (Microsoft 365 admin center › Agents › Tools › Work IQ MCP). Whether Microsoft's published client needs consent in a new tenant: further research needed.

    Your own desktop tool with its own harness: recommended setup
    
      
    1. Your app registrationA public client for your tool with delegated WorkIQAgent.Ask. On Windows, add the broker redirect to sign in through WAM.
    2. Your desktop toolMSAL interactive sign-in in the system browser or WAM. No secret in the app.
    3. Microsoft Entra IDIssues a token for WorkIQAgent.Ask.
    4. Work IQRemote MCP when your harness picks the tools; A2A or REST when Work IQ's agent should answer.

    Remote MCP with your own registration
    
      
      
        
    1. Register a public client: the Mobile and desktop platform, redirect http://localhost, public client flows allowed. Add the delegated Work IQ permission WorkIQAgent.Ask and grant admin consent. Work IQ is listed under APIs my organization uses once it's enabled.
      2. 
        
    2. Sign in with MSAL: authority https://login.microsoftonline.com/{tenant-id}, scope api://workiq.svc.cloud.microsoft/WorkIQAgent.Ask. Keep the token in MSAL's cache and renew it silently.
      3. 
        
    3. Send it as Authorization: Bearer … on every Streamable HTTP request to https://workiq.svc.cloud.microsoft/mcp. The endpoint's OAuth metadata advertises exactly this scope and the organizations authority.
      4. 
        
    4. For users in other tenants, register the app as multitenant: each tenant's admin consents, and users sign in through their home tenant, as Microsoft documents.
      5. 
      
    
      
    In this app, enter your tenant ID and client ID in Connections; remote MCP then signs in with your registration on any localhost port. The code is in the Code tab: src/auth.js for MSAL, src/workiq/mcp.js for the token on each request. Not yet tested in this app with a custom registration.
    
    
    
    
      
      
    • Recommendation: use your own registration rather than Microsoft's published MCP client. Consent prompts and sign-in logs then show your tool's name, and you control its redirects and platforms.
      • 
      
    • Bundling the Work IQ CLI also works, as this app shows, but it signs in with Microsoft's registration, each user accepts its EULA, and your tool runs an extra process. Check its license terms before you ship it in a product.
      • 
      
    • If your harness runs on a server, Microsoft's quickstart points to a confidential client with a secret or certificate and the On-Behalf-Of flow.

    Why this app runs without its own app registration
    
    
      
      
    • Local MCP: the Work IQ CLI brings Microsoft's own registration. This app only starts it and never sees the token.
      • 
      
    • Remote MCP: it uses the public client ID Microsoft publishes in its Work IQ MCP plugin (ba081686-5d24-4bc6-a0d6-d034ecffed87, oauthPublicClient: true, redirectPort: 12798). A public client has no secret, and the sign-in returns to port 12798, where this app listens.
      • 
      
    • The model: the Azure CLI is Microsoft's own client too.
      • 
      
    • Both MCP routes work here because this tenant already allows them: Work IQ is enabled, the user is in a billing policy, and both clients may sign in. For the CLI, Microsoft documents admin consent as a prerequisite. For the published MCP client in a new tenant: further research needed.
      • 
      
    • A2A and REST do need a registration. This app doesn't reuse Microsoft's MCP client for them; Microsoft's A2A quickstart has you register your own app.

    Further research needed
    
    
      
      
    • Changes through natural-language requests. Microsoft documents no create, update, delete or action operations for A2A, REST or MCP's ask. Yet WorkIQAgent.Ask "includes read and write access to Microsoft 365 resources that are accessible to Work IQ agents", and the default A2A agent card describes an assistant for "managing emails, scheduling meetings, and organizing documents". Whether an agent changes data when asked, and under which controls, isn't documented.
      • 
      
    • The MCP policy in effect in a tenant. Microsoft documents: "By default, mutation operations aren't allowed". In our test tenant on 23 September 2026, a do_action request with a made-up message ID returned Microsoft Graph's ErrorInvalidIdMalformed, so nothing was sent. This proves only that the request wasn't blocked before Graph checked it; it doesn't show whether the policy was off, set to allow the action, or evaluated at another stage. When the Policy tab is available, check Microsoft 365 admin center › Agents › Tools › Work IQ MCP › Policy. A change can take up to 24 hours.
      • 
      
    • Policy for A2A and REST. Microsoft says the policy layer "can apply across Work IQ experiences", but documents it only for MCP tool requests.
      • 
      
    • Which permissions MCP uses. Microsoft's MCP overview mentions four broad OAuth permissions, while the permissions reference lists only WorkIQAgent.Ask.
      • 
    
    
    
    In this app, the MCP harness gives the model ask, fetch, call_function, search_paths, get_schema and list_agents, and withholds create_entity, update_entity, delete_entity and do_action. Whether an ask request can change data is further research needed. Withholding tools in code is not an authorization boundary.
